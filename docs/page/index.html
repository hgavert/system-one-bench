Open-source Jev reproductions, zero-shot on real sentiment

Jev answers typed questions with probabilities instead of generating text. Within a week of its release, dozens of open reproductions appeared. We take every well-ranked one that runs on a 32 GB Apple M5, plus the newly released Decider 4B v2, GLiNER2.5-Decide and CLM, ask each the same sentiment question about 300 human-labelled tweets, and race them against local LLMs in LM Studio. The main comparison is zero-shot, with no training for the task. A reference section documents three models we also trained on tweets.

What a System One model does

You send a state (here, a tweet) and typed questions whose answer space you declare up front. You get back one answer per question, with a probability for every option, from a single forward pass. Nothing is generated, so there is nothing to parse.

SENTIMENT_QUESTION = {
    "type": "choice",
    "instructions": "What is the overall sentiment of this message?",
    "criteria": {
        "negative": "unhappy, angry, disappointed or critical",
        "neutral":  "factual or mixed, no clear feeling",
        "positive": "happy, grateful, excited or praising",
    },
}
# every engine below receives exactly this dict, and returns e.g.
{"choice": "positive", "probabilities": {"negative": 0.01, "neutral": 0.04, "positive": 0.95}}

The dataset

TweetEval sentiment (SemEval-2017 Task 4A): short, noisy social-media messages, each labelled negative, neutral or positive by human annotators. We use a seeded, class-balanced sample of 100 per class from the test split, so always answering "neutral" would score 33%.

Hello world with the simplest one

Laya is the easiest reproduction to start with: pip install laya, no server, 421M parameters.

import laya

agent = laya.load("convaiinnovations/laya")      # ~840 MB once, then cached; picks cuda > mps > cpu

questions = {"sentiment": {
    "type": "choice",
    "instructions": "What is the overall sentiment of this message?",
    "criteria": {
        "negative": "unhappy, angry, disappointed or critical",
        "neutral":  "factual or mixed, no clear feeling",
        "positive": "happy, grateful, excited or praising",
    },
}}

ans = agent.predict(msg, questions)["answers"]["sentiment"]

ECE = expected calibration error of the top-class probability (lower = the probabilities can be taken literally). An LLM returns a bare label, so its "confidence" is always 1.0 and its ECE equals its error rate.

Coverage. Every model in the table above was run on all 300 tweets. Decider 4B v2, GLiNER2.5-Decide (340M, 1B) and CLM 8B were added later, after the option-order test and the cascade had been run, so those two sections cover only some of the models.

Where the errors are

Every model confuses polar tweets with neutral ones far more than negative with positive. Laya and Kev hedge towards "neutral". The stock-model letter techniques and the LLMs lean the other way and push neutral tweets into a polarity. Decider is the most balanced: 73–75 correct in every class.

Does option order change the answer?

"One score per option" doesn't mean options are scored in isolation. Each option's vector is computed while reading the whole sequence, so position encodings, left-to-right attention and letter priors can leak in. We reran the 300 tweets with the three options in all 6 orders (1,800 decisions per model):

Only Laya has a consistent pull (towards the first option). SemIf has no preferred position but flips almost a fifth of its answers when the order changes. Decider, trained on shuffled options, is nearly order-blind. The bi-encoder CLM is order-blind by construction.

The LLMs above got a system prompt that defines the three classes. Here is the same run with the bare instruction Classify the following text to be either negative, neutral or positive. followed by the tweet in one user message, with the same enum schema:

Paired McNemar test on the same 300 tweets. Only Qwen's difference is beyond noise: with the descriptions it filed 25 positive tweets as "neutral", reading "mixed" broadly. Without them, 14. The bare prompt is also faster, since there's less to read.

Isn't this just embeddings?

A natural simplification: embed each "label: description" string, embed the tweet, pick the closest. That is a real method, and CLM is a trained version of it. Measured on the same tweets:

CLM's accuracy depends strongly on how the options are worded (0.433–0.550 across four phrasings, each collapsing towards a different class; standard phrasing shown). Its heads were trained on question–answer pairs and agent actions, not on affect. Raw last-token embeddings sit in a narrow cone (two unrelated tweets have cosine 0.95), so plain cosine picks the same option for nearly every tweet.

The difference is where the comparison happens:

Embedding nearest-neighbourSystem One model
Encodingtweet and each description encoded separately (bi-encoder)question, options and tweet in one sequence (cross-encoder)
Does the tweet's vector know the question?no: one vector per text, whatever you askyes: every token attends to the question and options

The answer still comes out as "which option fits best". But in a System One model each option's score is computed after the model has read this tweet and this question together, which is why the same tweet can be asked about sentiment, urgency or refunds and get a different, focused answer each time.

How each family picks an answer

Encoder + head (Laya): one marker per option

laya.common.build_sequence packs the question, the options and the message into one sequence. Each option starts with a [MASK] token whose position is recorded as a marker:

Drawn as rows for readability. The model sees one flat sequence in this order. The question and options are capped at 192 tokens and the whole sequence at 512.

h = encoder(input_ids, attention_mask).last_hidden_state    # ModernBERT-large, bidirectional
m = gather(head(h + type_emb(qtype)), marker_pos)           # one vector per option's [MASK]
p = softmax(scorer(m) / temperature)                        # one scalar per option, calibrated

LoRA + pointer (Kev): questions in isolated branches

Kev packs <state> tweet followed by, for every question, <q> instruction <opt> negative… </opt> <opt> neutral… </opt> … <decide>. A block-causal mask stops questions from seeing each other. The hidden state at <decide> is dotted with the state at each </opt>:

z = (W_k · h[</opt>_i]) @ (W_q · h[<decide>]) / sqrt(d)      # PointerHead, one logit per option
p = softmax(z / T)                                           # T ≈ 2.1–2.4, fitted per checkpoint

Letter logits (SemIf, openvons, Decider): let the LM name a letter

The simplest idea of all. Relabel the options A, B, C, run one forward pass, and read the next-token logits of the letter tokens. SemIf and openvons do this with a stock model and no training. Decider fine-tunes the model to answer in that slot.

# SemIf (MLX): the whole technique
prompt = chat([system, json.dumps({"evidence": tweet, "criterion": question,
                                   "options": [{"letter": "A", "description": "negative: unhappy…"}, …]})])
logits = model(prompt_ids)[0, -1]                  # next-token distribution, nothing generated
p = softmax(logits[[id("A"), id("B"), id("C")]])

# openvons: the same over any OpenAI-compatible server (vLLM, or mlx_lm.server on a Mac)
POST /v1/chat/completions  {"max_tokens": 1, "logprobs": true, "top_logprobs": 5, …}
p = softmax(logprob["A"], logprob["B"], logprob["C"])

Compared with asking an LLM for a JSON label, this gets a distribution instead of one sample, and it costs a single prefill with no decoding loop.

Decider's "head" is the LM's own output layer. It reads the next-token logits at the final ( of … (A) … (B) … (C) … Answer: (, restricted to the rows for label tokens: a fixed 255 × 2048 slice (A–Z, AA, AB, …) with unused letters masked, and no new parameters. That is why choice questions cap at 255. Its training shuffles the options every example, so a letter carries no information.

One score per option, any number of options

A classic classifier head is Linear(hidden, N), with one output row per class baked into the weights. A System One head outputs one number per option instead, from a shared function applied to each option's vector after one forward pass over the whole sequence. 5 options give 5 scores and 15 give 15, with the same weights and no retraining.

One adapter per engine, one harness

Each reproduction pins its own torch or MLX build, so each runs in its own environment. An engine that speaks TypeSafe's /v1/systemone (Kev) gets the question dict over HTTP. The others get a small adapter that reads the same data/test_tweets.jsonl and writes {"pred", "probs", "latency_ms"} per tweet, scored by the same code as everything else.

For reference: the trained models

Earlier in this project we also fine-tuned Laya and two Kev models on the tweets. That isn't the point of a general decision model: with labelled data you could just train a classifier head on sentence embeddings. It does show how far each architecture goes when you have data. All three trained on the same 3,000 training tweets (1,000 per class, TweetEval train split), one epoch, with the same question dict, then had their temperature refitted on 300 validation tweets. None of them saw the 300 test tweets.
